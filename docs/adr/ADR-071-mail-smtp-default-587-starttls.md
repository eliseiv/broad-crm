# ADR-071: Дефолт формы добавления ящика — SMTP `587` / STARTTLS (не `465` / SSL)

Статус: accepted · Дата: 2026-08-05

## Контекст

Форма добавления почтового ящика (`MailboxFormModal`, режим `add`) предзаполняла SMTP
**портом `465` и защитой `SSL`**. На проде это приводит к **невозможности подключить ящик**:
пользователь добавляет Gmail-ящик, агрегатор возвращает `422 smtp_login_failed`, форма CRM
показывает «Не удалось подключиться к SMTP».

**Причина (измерено orchestrator'ом командами с прод-хоста, не по памяти):**

- Прод-хост (Hetzner, `49.12.189.77`) **не имеет исходящего доступа (egress) на порт `465`**:
  `smtp.gmail.com:465` **таймаутит при коннекте** с хоста; `smtp.gmail.com:587`
  **коннектится**, Gmail принимает логин (SMTP код `235`).
- В host-iptables **блока по `465` нет** ⇒ фильтрация **upstream** (Hetzner), вне нашего контроля.
- `587`/STARTTLS — де-факто стандарт этой инфраструктуры: **все 120 живых прод-ящиков имеют
  `smtp_port=587`** (0 ящиков на `465`).
- Внешний контекст: агрегатор (**отдельный репозиторий**, в CRM его нет) уже стандартизирован
  на `587`/STARTTLS для password-провайдеров.
- Это **не регрессия недавнего деплоя** — SMTP-логику он не трогал (сверено по git).

**Важно про универсальность.** `465`/SSL **не является ошибочным в принципе** — это рабочий
SMTP-режим у многих провайдеров. Решение локально для **этого деплоя**, где host-egress на
`465` закрыт upstream, а `587`/STARTTLS поддерживают все перечисленные провайдеры и все
прод-ящики. Существуют провайдеры/серверы, где `587` не поддерживается — для них порт/защита
меняются вручную (см. Последствия).

## Решение

1. **Нормативный дефолт формы создания ящика:**
   - `smtp_port = 587`
   - защита = **STARTTLS** (`smtp_ssl = false`, `smtp_starttls = true`)
   - (прежний дефолт `465` / SSL / `smtp_ssl = true` — **отменён**).

2. **IMAP-дефолт не меняется** — `993` / SSL (993 работает, 120 ящиков синкаются).

3. **Нормативная таблица онбординга** «Подсказки по провайдерам»
   ([08-design-system.md §«Как добавить почту?»](../08-design-system.md#инструкция-как-добавить-почту-нормативно-adr-045))
   приведена к `587`/STARTTLS в строках Gmail, Яндекс, Mail.ru, Yahoo и «Другой провайдер».
   iCloud (`smtp.mail.me.com:587 STARTTLS`) уже соответствовал — образец, не менялся.

## Область (что НЕ меняется)

- **Контракт API не затронут.** `POST /api/mail/mailboxes` по-прежнему требует
  `smtp_port` (`1..65535`) и взаимоисключающие булевы `smtp_ssl` / `smtp_starttls`
  ([04-api.md](../04-api.md), [ADR-044](ADR-044-mail-full-merge-into-crm.md) §схема). Меняется
  **дефолтное значение формы**, а не форма/валидация контракта.
- Пользователь может **вручную** сменить порт и защиту (поля формы остаются) — для провайдера,
  которому нужен `465`/SSL или иной порт.
- IMAP host/port/security, RBAC, поток онбординга, Outlook-OAuth ([ADR-045](ADR-045-mail-outlook-oauth-headless-reonboarding.md)) не тронуты.

## Последствия

- **Прод-баг устранён**: Gmail и прочие ящики подключаются с дефолта (`587`/STARTTLS проходит
  egress хоста; провайдеры принимают логин).
- Все перечисленные в таблице провайдеры (Gmail, Яндекс, Mail.ru, Yahoo, iCloud) поддерживают
  `587`/STARTTLS — дефолт универсален для них.
- Провайдер/сервер, требующий `465`/SSL, остаётся подключаемым **вручную** — норма не запрещает
  `465`, лишь снимает его с дефолта.
- Требуется правка **frontend** (`MailboxFormModal.tsx`) — зона frontend, вынесена в `next_actions`
  (docs описывают целевую норму; код приводится следующим шагом).

## Альтернативы

- **Открыть egress на `465` на стороне Hetzner** — отклонено: зависит от upstream-firewall, который
  мы не контролируем; `587` и так стандарт всей инфры и агрегатора ⇒ смена дефолта проще и надёжнее.
- **Оставить `465` дефолтом, менять вручную** — отклонено: дефолт, который на этом хосте
  гарантированно таймаутит, воспроизводит прод-баг у каждого нового оператора.
- **Пер-провайдерные дефолты (часть на `465`)** — отклонено: единый `587`/STARTTLS соответствует
  всем 120 прод-ящикам и агрегатору; разнобой усложняет форму без выгоды.
