# ADR-072: CRM Admin API contract v1.1 «экономика» — страница «Продукты и тарифы», ключ каталога `backend-economics`, детекция расширения

- **Статус:** accepted
- **Дата:** 2026-08-06
- **Отношение к [ADR-069](ADR-069-backend-users-page-admin-contract.md):** §3 («CRM — прокси без хранилища») **подтверждается, НЕ супессируется**; §7 (маппинг ошибок контракта) **амендируется** — см. §4 ниже. Остальные пункты ADR-069 действуют без изменений.

## Контекст

Страница «Юзеры бэков» ([ADR-069](ADR-069-backend-users-page-admin-contract.md)) показывает пользователей внешних сервисов и историю их запросов, но не показывает **экономику**: сколько токенов даёт каждый продукт, сколько токенов списывается за генерацию (чат/фото/видео) и во сколько запрос обошёлся у провайдера. Сегодня в контракте v1 этих величин нет вовсе:

- `GET {P}/products` отдаёт только `product_id`/`name`/`price`/`period` — без количества токенов;
- тарифов списания в контракте нет ни в каком виде;
- элемент истории запросов не несёт ни списанных токенов, ни себестоимости.

Изменить эти значения оператор не может: у бэков они лежат либо в коде (коммит + деплой), либо в БД без admin-CRUD. Требование владельца: оператор видит продукты и тарифы бэка с количеством токенов, **меняет** эти значения из CRM и видит в истории запросов пользователя списанные токены и USD-себестоимость каждой генерации.

Решения владельца, принятые до этого ADR и не пересматриваемые здесь: источник истины — БД самого сервиса; редактируются только **токены продукта** и **тариф списания** (цена в деньгах и allowlist выдачи — нет); UI — **отдельная страница**; сводная маржа за период не нужна, себестоимость нужна на уровне отдельного запроса.

## Решение

### §1. Контракт расширяется до **v1.1 «экономика»** — аддитивно, имена заморожены

Контракт v1 не переписывается: v1.1 = v1 **плюс** перечисленное ниже. Бэк, реализующий только v1, остаётся полностью совместимым (см. §4 — деградация). Обе стороны (CRM и каждый подключаемый сервис) реализуются разными командами в разных репозиториях, поэтому **имена путей и полей заморожены**: расхождение в имени поля даёт молча пустой экран, а не ошибку.

Всё под существующим `X-Admin-Key`, под автоопределяемым префиксом `P` ∈ {`/api/billing/admin`, `/v1/admin`}. Даты — ISO 8601 UTC, ошибки бэка — `{"detail": ...}`.

| Метод + путь (у бэка) | Статус в v1.1 |
| --- | --- |
| `GET {P}/products?scope=grantable\|all` | **расширен** |
| `PATCH {P}/products/{product_id}` | **новый** |
| `GET {P}/pricing` | **новый** |
| `PATCH {P}/pricing/{tariff_id}` | **новый** |
| `GET {P}/capabilities` | **новый**, опциональный |
| `GET {P}/users/{id}/requests` | **расширен** |

**`GET {P}/products` → `{"items":[…]}`**, элемент: `product_id`, `name`, `price` (str\|null), `period` (str\|null), **`tokens`** (int), **`avatar_tokens`** (int\|null — вторая валюта, есть не у всех бэков), **`grantable`** (bool), **`updated_at`** (ISO\|null; `null` = «ни разу не менялось»).
Параметр **`scope` по умолчанию `grantable`** — это **сохраняет сегодняшнее поведение** формы «Установить план» на странице «Юзеры бэков»; страница «Продукты и тарифы» зовёт `scope=all`. Все новые поля элемента **опциональны для читателя**: бэк уровня v1 их не отдаёт, и это не ошибка.

**§1.1. Поведение на бэке уровня v1 — нормативно, ОДНО (не на усмотрение исполнителя).** `GET {P}/products` — **v1-путь**: у бэка без расширения он отвечает **`200`** без новых полей, значит состояние «расширение не поддерживается» через `404` для таблицы «Продукты» **недостижимо в принципе** (в отличие от `/pricing`, которого у такого бэка нет вовсе). Без явного правила исполнитель обязан догадаться, что рисовать в колонках «Токены»/«Выдаётся», и любая догадка даёт неверный экран, а не ошибку. Норма:

1. **CRM нормализует отсутствующее поле в `null`** и **никогда** не отвечает `502` из-за его отсутствия. В схеме ответа CRM `tokens`, `avatar_tokens`, `grantable`, `updated_at` — **nullable** ([04-api.md#backend-economics](../04-api.md#backend-economics)).
2. **`tokens = null` (поле не отдано) ⇒ ячейка «Токены» = `—`, строка read-only** (карандаш не рендерится **ни при каком** праве и ни при каких `features`): править нечего — CRM не знает текущего значения, а `PATCH` без него превратился бы в слепую установку.
3. **`grantable = null` ⇒ `—`**, а **не** «Нет»: это «не отдано», а не «не выдаётся». Тот же принцип, что у `provider_cost_usd` (§5) — неизвестное не выдаётся за отрицательное значение.
4. **`items` непуст И НИ ОДИН элемент не несёт `tokens` ⇒ таблица «Продукты» переходит в тот же информационный блок «бэк не поддерживает расширение»**, что и таблица «Тарифы списания». Это и есть обещанная §Последствиями деградация на v1-бэке: обе таблицы выглядят одинаково, потому что причина одна. **`items: []` под это правило НЕ подпадает** — пустой каталог есть пустой каталог (empty state), а не отсутствие расширения.
5. **Асимметрия products ↔ pricing — намеренная и обязана быть названа:** `GET {P}/products` — путь v1, поэтому его новые поля опциональны; `GET {P}/pricing` — путь, существующий **только** в v1.1, поэтому его поля (`tariff_id`, `kind`, `tokens`) **обязательны**: `200` без них = contract mismatch → `502 backend_admin_unavailable` (не `—`, не read-only).

**`PATCH {P}/products/{product_id}`** — тело `{"tokens": int≥0, "avatar_tokens": int≥0|absent, "if_updated_at": ISO|absent}`, хотя бы одно значимое поле. Ответ: элемент продукта + **`previous_tokens`** + **`changed`** (bool) + **`effective_after_seconds`** (int).

**`GET {P}/pricing` → `{"items":[…]}`**, элемент: **`tariff_id`** (str, **opaque для CRM** — ключ пути `PATCH`), **`kind`** ∈ `chat|photo|video|other`, `name` (str\|null), **`tokens`** (number), `updated_at` (ISO\|null). `kind` даёт CRM разбивку «чат/фото/видео» без знания внутренних имён типов конкретного бэка; ключом остаётся `tariff_id`, потому что типов у бэка может быть больше трёх.

**`PATCH {P}/pricing/{tariff_id}`** — тело `{"tokens": number≥0, "if_updated_at": ISO|absent}`. Ответ: элемент тарифа + `previous_tokens` + `changed` + `effective_after_seconds`.

**`GET {P}/users/{id}/requests`** — элемент дополняется: **`tokens_spent`** (number\|null), **`provider_cost_usd`** (number\|null), **`refunded`** (bool).

> ⚠️ **Два уровня типа — не путать (частый источник ошибки реализации).** Здесь описан **контракт БЭКА уровня v1.1**: он `refunded` отдаёт **всегда**, поэтому тип — `bool`. **Схема ОТВЕТА CRM — шире: `bool | null`** ([04-api.md](../04-api.md#backend-users)), потому что бэк уровня **v1** этого поля не отдаёт вовсе, а CRM нормализует отсутствующее поле в `null` (§1.1) и `502` из-за него не отвечает. **`null` ≠ `false`:** «не отдано» — не «возврата не было». Для `tokens_spent`/`provider_cost_usd` уровни совпадают по типу (`number|null` в обоих), но `null` там покрывает **два** случая сразу — «не измерено» (инвариант 1) и «не отдано» (v1); различать их CRM не может и не пытается — оба рендерятся `—`.

**`GET {P}/capabilities`** → `{"contract_version":1, "features":[…], "limits":{…}, "cache_effective_after_seconds":int}`. Допустимые значения `features`: `products.read`, `products.write_tokens`, `pricing.read`, `pricing.write_tokens`, `requests.costs`. **404 на этом пути = «расширений нет»** (см. §4).

**Разрешённые конфликты именования (зафиксировано, не пересматривать):**

- **`/pricing`, а не `/tariffs`**: в CRM слово «тариф» уже занято продуктами/планами (`BackendProduct` документирован как «Тарифы бэка» — [04-api.md#backend-users](../04-api.md#backend-users)). Ключ пути при этом остался **`tariff_id`** — как предложила сторона сервиса.
- **`tokens_spent`/`provider_cost_usd`, а не `tokens_cost`/`usd_cost`**: имена контракта не должны повторять имена колонок конкретного сервиса. `refunded` принят как есть.
- **И probe-детекция, и `/capabilities`**: probe обязателен технически (без него 404 маппится неверно, §4), `/capabilities` даёт список фич и лимиты для валидации формы. Одно не заменяет другое.

**Поведенческие инварианты — часть контракта:**

1. **`provider_cost_usd = null` означает «не измерено», а НЕ ноль** — см. §5.
2. **`refunded: true`** — списание возвращено; `tokens_spent` при этом **остаётся заполненным** (возврат фиксируется отдельно, а не обнулением стоимости). Без флага оператору показывалось бы списание, которого уже нет.
3. **404 на расширенном пути = исключительно «эндпоинт не реализован»**; неизвестный `product_id`/`tariff_id` на реализованном эндпоинте → **400** — см. §6.
4. **`GET {P}/products` обязан работать и без расширения** — CRM использует его как probe-путь детекции префикса (§4).
5. **`PATCH` идемпотентен** (устанавливает значение, а не дельту) — ключ идемпотентности не нужен. Повтор с тем же значением → `changed: false`, `updated_at` не двигается, аудит на стороне бэка не пишется.
6. **Поддержка записи выводится только из `features`**, не из наличия поля `tokens`: бэк вправе отдавать токены read-only — см. §7.
7. Конфликт `if_updated_at` → **409** (см. §4, код `backend_admin_conflict`). Списки `products`/`pricing` **не пагинируются**; CRM отвергает ответ, содержащий **> 500** элементов, как contract mismatch (`502 backend_admin_unavailable` — «не-контрактные данные»).
8. **`X-Admin-Actor`** — опциональный заголовок (≤255 символов), CRM шлёт `crm:<user_uuid>`. Это **заявление, а не аутентификация**: значение ничем не подтверждается и не проверяется бэком. Формулировку обязаны нести докстрока клиента и описание заголовка в module-docs — иначе на нём построят отчёт «кто менял» как на достоверном источнике.

### §2. Отдельная страница «Продукты и тарифы» и отдельный ключ каталога `backend-economics`

**Новая страница каталога прав `backend-economics` с действиями `view` / `edit`** ([ADR-021](ADR-021-rbac-users-roles.md)), в `CATALOG` — сразу после `backend-users`. Новый пункт плоской навигации «Продукты и тарифы» (`/backend-economics`), новый роутер `/api/backend-economics` — а **не** расширение `backend-users`.

**Почему не `backend-users:edit`:**

- `backend-users:edit` — операция **над одним пользователем** конкретного бэка (начислить ему токены, выдать план). Правка каталога продуктов и тарифов — **глобальное изменение**, влияющее на **все будущие покупки и все будущие генерации** всех пользователей этого бэка. Держатель права «поправить баланс клиента» не обязан получать право «переписать цену всем».
- Ресурсы **не вложены в пользователя**: `products`/`pricing` — самостоятельные коллекции бэка, у них нет `user_id` в пути. Втаскивание их в роутер `backend_users.py` дало бы эндпоинты, у которых имя роутера противоречит содержимому.
- Гейты разные ⇒ роутеры разные: одна и та же зависимость `require("backend-users", …)` на всех путях роутера — сильная сторона текущей реализации, ломать её ради экономии одного файла не следует.
- **Миграции не требуется**: `roles.permissions` — `jsonb`, добавление ключа аддитивно; супер-админ получает право через `full_catalog_permissions()`, остальные роли — fail-closed (право отсутствует, пока его явно не выдали).

**Цена решения:** оператору, которому нужны обе функции, роль обязана содержать оба ключа; замороженный контракт-тест каталога прав правится в том же проходе (иначе CI красный).

### §3. CRM остаётся прокси без собственного хранилища — [ADR-069](ADR-069-backend-users-page-admin-contract.md) §3 **подтверждается**

Ни продукты, ни тарифы, ни себестоимость **не** копируются в БД CRM: собственных таблиц и миграций модуль не добавляет, значения читаются на лету и пишутся напрямую в бэк. Причина та же, что в ADR-069 §3, и здесь она сильнее: продукт и тариф — **денежные величины**, у которых недопустимо два дома. Копия в CRM означала бы, что при расхождении неизвестно, по какому значению бэк реально начислил токены.

Отклонено: кэш каталога продуктов в БД CRM «для скорости» (устаревание денежной величины дороже одного HTTP-запроса); собственная таблица аудита значений (аудит пишется событием, см. §10, а история значений — забота бэка).

**Следствие, которое обязано быть видимым оператору:** у бэка правка применяется не мгновенно (у него свой кэш каталога между процессами). Поэтому ответ `PATCH` несёт **`effective_after_seconds`**, а CRM **показывает эту задержку оператору** в тосте успеха (§ [08-design-system.md](../08-design-system.md#страница-продукты-и-тарифы-нормативно-adr-072)). Невидимость окна рассинхрона, а не его длительность, делает расхождение дорогим.

### §4. Детекция расширения и разведение семантики 404 (**амендмент [ADR-069](ADR-069-backend-users-page-admin-contract.md) §7**)

В v1 у 404 от бэка было два смысла — «контракт не реализован» (при детекции префикса) и «пользователь не найден» (на путях `/users/*`). С появлением расширенных путей смыслов становится **три**, и их обязано разводить не «по месту вызова», а явным параметром.

**(а) Probe детекции префикса разводится с вызовом расширения.** Детекция префикса выполняется **всегда по v1-пути `GET {P}/products`** (инвариант 4 §1) и только по нему. Расширенные вызовы (`/pricing`, `PATCH`, `/capabilities`) идут **только против уже определённого префикса**. Без этого разведения первый же вызов расширения при холодном кэше даёт 404 на обоих кандидатах ⇒ CRM объявляет бэк не реализующим контракт **и не кэширует префикс вовсе** — при том, что v1 у бэка работает.

**(б) Семантика 404 задаётся вызывающим явно, без умолчания.** Клиент бэков принимает **обязательный** (без значения по умолчанию) параметр семантики 404 с тремя исходами:

| Семантика | Когда применяется | Код CRM |
| --- | --- | --- |
| `CONTRACT` | детекция префикса по v1-probe; 404 на **известном** префиксе на v1-пути, не относящемся к пользователю | `502 backend_admin_not_supported` |
| `USER` | пути **`/users/*`** (карточка, платежи, запросы, `POST` токенов/подписки) | `404 backend_user_not_found` |
| `EXTENSION` | **расширенные пути v1.1**: `PATCH /products/{id}`, `GET`/`PATCH /pricing`, `GET /capabilities` | **`502 backend_admin_extension_not_supported`** |

**Отсутствие значения по умолчанию — это гейт, а не стилистика:** каждый новый метод клиента обязан решить вопрос явно. Иначе копипаст существующего метода (где семантика «пользователь» зашита) воспроизводит ложное «Пользователь не найден» на странице, где пользователя нет вообще.

**§4а.1. Probe выполняется при ЛЮБОМ холодном вызове, включая v1-пути — подтверждено, с двумя названными следствиями.** «Всегда по v1-пути и только по нему» читается буквально: при пустом кэше префикса CRM сначала делает probe `GET {P}/products` и лишь затем — запрошенный путь, **какой бы он ни был** (в том числе `/users*` страницы «Юзеры бэков»). Это **не** побочный эффект, а условие корректности: пока префикс неизвестен, `404` **любого** пути двусмыслен.

- **Следствие 1 (цена): один дополнительный upstream-запрос** на первый вызов процесса к каждому бэку. Укладывается в уже принятую [ADR-069](ADR-069-backend-users-page-admin-contract.md) §2 цену «до одного лишнего запроса после рестарта».
- **Следствие 2 (изменение поведения): неработающий `/products` при рабочем `/users` теперь блокирует страницу «Юзеры бэков»** (`502 backend_admin_not_supported`), тогда как прежде она бы работала. Принято: `GET {P}/products` — **обязательный** путь контракта v1 и нормативный probe (инвариант 4 §1), поэтому такой бэк контракт нарушает; молча обслуживать его вполсилы значит скрывать дефект интеграции.
- **Побочно закрывается латентный дефект v1**, ради которого перечисленная цена и платится: в прежней схеме при холодном кэше `404` от `GET /users/{id}` **несуществующего** пользователя уводил в перебор префиксов и заканчивался `backend_admin_not_supported` — семантика `USER` в ветке детекции **не учитывалась вовсе** (в `_request` ветка детекции — та, что перебирает `PREFIX_CANDIDATES` при пустом кэше, — параметр семантики 404 не читала вовсе). Оператор видел «бэк не поддерживает контракт» вместо «пользователь не найден» — ровно на первом запросе после рестарта. С probe первым идёт `/products`, префикс кэшируется, и `404` от `/users/{id}` попадает уже в ветку известного префикса.

**(в) Два новых кода ошибок CRM** (рядом с существующими `backend_admin_*` — [04-api.md#backend-economics](../04-api.md#backend-economics)):

| Код | HTTP | Сообщение | Когда |
| --- | --- | --- | --- |
| `backend_admin_extension_not_supported` | **502** | «Бэк не поддерживает расширение контракта» | 404 на расширенном пути v1.1 при **известном** префиксе |
| `backend_admin_conflict` | **409** | «Значение изменил другой оператор — обновите страницу» | бэк ответил **409** (конфликт `if_updated_at`) |

`409` от бэка сегодня схлопывается в безликое «Ошибка бэка (HTTP 409)» с кодом `backend_admin_unavailable` — оператор не понимает, что делать. Новый код даёт UI однозначное действие: тост «обновите страницу» + refetch.

**(г) `backend_user_not_found` действует только на путях `/users/*`.** С этого ADR код `backend_user_not_found` **недостижим** с роутера `/api/backend-economics` — в нём нет ни одного пути, содержащего пользователя. Появление этого кода на странице «Продукты и тарифы» = дефект, а не состояние.

### §5. `provider_cost_usd = null` = «не измерено», и это нормативно

`provider_cost_usd` — фактическая себестоимость генерации у провайдера. **`null` означает «не измерено» и НЕ означает ноль.** Нормы:

- UI обязан рендерить **`—`**, и **никогда `$0.00`**.
- `value || 0`, `?? 0`, `coalesce` и любое иное схлопывание `null` в число **на уровне строки запрещены** — они превращают «мы не знаем» в «бесплатно».
- Настоящий ноль (`0`) — это измеренная нулевая стоимость, и он рендерится **`$0.00`**, отличимо от `—`.
- Формат денег — с точностью до **4 знаков** после запятой: глобальный `toFixed(2)` схлопнул бы `$0.0004` в `$0.00`, то есть то же враньё с другой стороны.
- Если хоть одна строка таблицы содержит `—`, под таблицей рендерится **легенда** («— — себестоимость не измерена»): различие не должно передаваться только цветом (a11y, NFR-8).

Та же норма распространяется на `tokens_spent` (`null` → `—`).

### §6. 404 на расширенном пути = только «не реализовано»; неизвестный id → 400

**Неизвестный `product_id`/`tariff_id` на реализованном эндпоинте обязан давать `400` с `detail`, а не `404`.** Иначе CRM не отличает опечатку в идентификаторе от отсутствия расширения у бэка и показывает оператору «бэк не поддерживает расширение» там, где бэк его поддерживает.

Транзит в CRM: `400` от бэка → **`400 backend_admin_bad_request`** с сообщением бэка (существующий код, поведение не меняется).

Симметрично: **`PATCH` никогда не создаёт строк** — правка каталога есть правка существующего элемента; «создать продукт из CRM» в scope не входит.

### §7. Поддержка записи выводится из `features`; без `/capabilities` модуль работает read-only

Признак «эту величину можно править» CRM берёт **только** из `features` ответа `GET {P}/capabilities`:

- `products.write_tokens` ∈ `features` ⇒ доступна правка токенов продукта;
- `pricing.write_tokens` ∈ `features` ⇒ доступна правка тарифа списания.

Наличие поля `tokens` в ответе **признаком записи не является** — бэк вправе отдавать токены read-only.

**Нормативное следствие (решение этого ADR):** `GET {P}/capabilities` опционален **для чтения**, но **обязателен для правки**. Бэк, у которого CRM не получила подтверждённых фич, работает **read-only**: таблицы рендерятся, если пришли `products`/`pricing`, но контролы правки не рендерятся ни при каком праве. Это fail-closed: показать карандаш там, где `PATCH` не реализован, значит обещать оператору операцию, которая упадёт.

**§7.1. `capabilities: null` = «фич НЕ подтверждено», а не только «404».** Подзапрос `/capabilities` идёт **внутри** обработчиков `products`/`pricing`, и у него есть не один исход отказа. Нормативно: **ЛЮБОЙ неуспех подзапроса** — `404`, таймаут, `5xx`, `401`/`403`, невалидный JSON, ответ не по схеме — даёт **`capabilities: null`**, и **список при этом отдаётся** (`200`). Провалить весь список в `502` из-за необязательного эндпоинта запрещено: работающие данные не должны краснеть из-за факультативного подзапроса. Обратная цена принята осознанно: транзиентный сбой временно прячет карандаши у оператора с правом — это **безопасная** сторона ошибки (в отличие от карандаша, обещающего операцию, которая упадёт). Неуспех подзапроса **пишется в лог** с причиной, иначе «пропали карандаши» неотличимо от «бэк не поддерживает запись».

**Имя события лога — нормативно** (по образцу существующего именованного события клиента `backend_admin_prefix_detected` в `_remember_prefix` (`backend/app/infra/backend_admin_client.py`)): событие **`backend_admin_capabilities_unavailable`**, поля **`backend_id`** (str) и **`reason`**:

| `reason` | Исход подзапроса |
| --- | --- |
| `not_found` | `404` — эндпоинт не реализован |
| `timeout` | истёк таймаут чтения/соединения |
| **`transport`** | сбой транспорта **без ответа**: DNS, отказ соединения, TLS-ошибка (**это НЕ таймаут**) |
| **`redirect`** | **любой `3xx`** — клиент создаёт `httpx.AsyncClient(follow_redirects=False)` (`backend/app/infra/backend_admin_client.py`), поэтому редирект **достижим** и означает **ошибку конфигурации адреса** (http→https, канонический хост, слеш), а не сбой бэка |
| `rejected` | `401` / `403` — ключ не принят |
| **`http_4xx`** | прочие `4xx` (`400`, `409`, `405`, `422`, `429`, …) — кроме `401`/`403`/`404` |
| `http_5xx` | `5xx` |
| `bad_json` | тело не разбирается как JSON |
| `schema_mismatch` | JSON разобран, но не соответствует схеме |

**Перечень ЗАКРЫТ и обязан покрывать ВСЕ исходы.** Появление исхода, которому нет строки, — повод **расширить эту таблицу**, а не отнести его к ближайшему по смыслу: `reason` существует ради разбора инцидента, и DNS-сбой, помеченный `http_5xx`, посылает дежурного искать ошибку на стороне бэка, которого он даже не достиг; редирект, помеченный так же, — искать сбой там, где неверно записан адрес. Значения `transport`, `http_4xx` и `redirect` добавлены именно по этой причине — исходный перечень их не покрывал.

**Проверка полноты — по классам исхода, а не по памяти.** Каждый возможный исход подзапроса обязан попадать ровно в одну строку: **ответа нет** → `timeout` / `transport`; **есть HTTP-статус** → `3xx` = `redirect`, `401`/`403` = `rejected`, `404` = `not_found`, прочие `4xx` = `http_4xx`, `5xx` = `http_5xx`; **статус 2xx, но тело негодно** → `bad_json` / `schema_mismatch`. Ветка «прочее» в коде, сваливающая неопознанный исход в `http_5xx`, — **дефект**: она возвращает ровно ту ложную диагностику, ради устранения которой перечень и расширялся. Имя и перечень `reason` фиксируются именно здесь, потому что [06-testing-strategy.md](../06-testing-strategy.md#backend-users--backend-economics-adr-069--adr-072) делает логирование **ассертируемым** в каждом из перечисленных ниже исходов — **по кейсу на строку таблицы** (число кейсов намеренно не дублируется здесь: оно равно числу строк и меняется вместе с ней): без имени события `qa` ассертил бы свободный текст, и такой ассерт вырождается в «что-то залогировано», ломаясь от любой переформулировки. **Значение `X-Admin-Key` в событие не попадает** (общий инвариант §10).

**Состояние обязано быть видимо оператору с правом.** `capabilities: null` **неотличимо на экране** от «у меня нет права `edit`» и от «бэк не умеет писать»: карандаши просто исчезают, а лог доступен разработчику, а не оператору. Fail-closed-логика при этом **не меняется** — добавляется **нейтральная подсказка**, рендеримая **ТОЛЬКО** при `capabilities === null` **И** наличии `backend-economics:edit`: **«Правка недоступна: бэк не подтвердил поддержку изменения значений»** (без кнопки повтора, **не** ошибка; держателю только `view` **не показывается** — ему нечего объяснять). Иначе из трёх состояний таблицы различимы два, что противоречит и §3 этого ADR («невидимость окна, а не его длительность, делает расхождение дорогим»), и правилу дизайн-системы о различимости состояний. Нормативная строка и условие рендера — [08-design-system.md](../08-design-system.md#страница-продукты-и-тарифы-нормативно-adr-072).

**§7.2. `limits`: ИМЕНА КЛЮЧЕЙ И ТИПЫ — часть замороженного контракта; ЗНАЧЕНИЯ — НЕТ.** Состав ключей **ОБЯЗАН быть идентичен** на обеих сторонах; **согласован со стороной сервиса 2026-08-06**. Границы в примере ниже — **иллюстрация**, каждый бэк отдаёт свои (полное правило — сразу под примером). Проектный план состав не задавал, и без фиксации две команды разошлись бы молча. Пример структуры (**значения иллюстративные — см. предупреждение ниже**):

```json
"limits": {
  "product_tokens_max": 500000,
  "product_avatar_tokens_max": 50000,
  "tariff_tokens_max": 1000,
  "tariff_decimal_places": 6
}
```

> ⚠️ **ЗАМОРОЖЕНЫ ТОЛЬКО ИМЕНА КЛЮЧЕЙ И ТИПЫ. Числа выше — иллюстрация, а НЕ норма.** Границы — **runtime-данные каждого бэка**: каждый отдаёт свои, и они меняются без изменения контракта. Отсюда три запрета: **(1)** CRM **не хардкодит** ни одно из этих значений (константа в коде или в форме = молчаливая блокировка легитимной правки тостом «вне допустимого диапазона»); **(2)** тесты **не ассертят** конкретные числа — ассертить можно только имена ключей, типы и правило обработки; **(3)** значения из этого блока **не переносятся** в другие документы как нормативные. Подтверждение неиллюзорности риска: у единственной существующей реализации стороны сервиса верхняя граница токенных лимитов — **другого порядка** (`1_000_000_000`, факт установлен orchestrator'ом по коду сервиса), то есть числа выше **уже** разошлись бы с ней.

**§7.3. Отказ валидации у бэка — `422` наравне с `400` (замыкает путь деградации §7.2).** Клиентская валидация границ отключается, когда `limits` не пришли (§7.2), поэтому значение **реально доходит до бэка** — верхних границ в схемах запроса CRM нет намеренно. У контрагента отказ валидации тела — **`422`**, а не `400` (сторона сервиса: `422` — валидация тела, `400` — неизвестный `product_id`, `409` — конфликт `if_updated_at`; границы и точность заданы схемой запроса). Норма:

- **`400` И `422` от бэка ⇒ один и тот же код CRM `backend_admin_bad_request` (HTTP 400)** с транзитом текста причины. Для оператора это один класс: «бэк отверг введённое значение — исправьте ввод», и различать их в UI нечем и незачем. Отдельный код не вводится.
- **Оставлять `422` в общей ветке «прочий не-2xx» ЗАПРЕЩЕНО.** Там он превращается в `502 backend_admin_unavailable` с голым «Ошибка бэка (HTTP 422)»: красная ошибка «бэк сломан» вместо действия «поправьте число», по документированному и штатному пути. Это ровно тот класс, что уже устранён для `409` в §4в, — здесь он остался незакрытым.
- **Извлечение текста причины с учётом формата контрагента:** у FastAPI `detail` при `422` — **список** объектов (`{loc, msg, type}`), а не строка. Норма: если `detail` — строка, она транзитом идёт в сообщение; если **список** — берётся `msg` первого элемента (при наличии — с указанием поля из хвоста `loc`); если извлечь текст не удалось — **нормативный фолбэк «Бэк отверг значение: не прошло проверку на стороне бэка»**. Фолбэк обязателен: он всё равно называет причину и действие, в отличие от номера статуса.

**Незнакомый ключ `limits` CRM игнорирует** (forward-compatibility): появление у бэка нового ключа не является contract mismatch и не даёт `502` — он просто не участвует в клиентской валидации до тех пор, пока не будет внесён в контракт этим ADR.

| Ключ | Тип | Применение в CRM |
| --- | --- | --- |
| `product_tokens_max` | int | верхняя граница поля «Токены» продукта |
| `product_avatar_tokens_max` | int | верхняя граница поля «Аватар-токены» |
| `tariff_tokens_max` | number | верхняя граница поля «Токенов за генерацию» |
| `tariff_decimal_places` | int | максимум знаков после запятой у тарифа |

**Правило обработки — нормативно:** **отсутствующий ключ ⇒ CRM по нему клиентскую валидацию НЕ выполняет** и полагается на серверный отказ бэка — **`400` ИЛИ `422`**, оба маппятся в `backend_admin_bad_request` (см. §7.3). **`limits` отсутствует целиком или `capabilities: null` ⇒ клиентской валидации границ нет вовсе**, форма при этом остаётся полностью работоспособной. Нижняя граница `≥ 0` и «число/целое» — собственная валидация CRM, она от `limits` не зависит и действует всегда.

**Почему конверт, а не отдельный CRM-эндпоинт.** Мотив — **атомарность снимка**: список и его write-аффорданс обязаны приходить **одним** ответом, иначе таблица и карандаши в ней разъезжаются во времени (список свежий, фичи — от прошлого запроса, или наоборот). Экономией запросов конверт **не мотивирован и её не даёт**: за загрузку страницы `/capabilities` запрашивается **дважды** (по разу в каждом из двух обработчиков) — **4** upstream-вызова против 3 при отдельном эндпоинте. Цена принята: это лёгкий `GET` без тела, а рассинхрон аффорданса стоит дороже. **В пределах ОДНОГО обработчика `/capabilities` запрашивается не более одного раза**; **межзапросного кэша фич не вводится** — кэш был бы ещё одним состоянием со своей инвалидацией (ср. [TD-078](../100-known-tech-debt.md)), а устаревшие фичи дают ровно тот дефект, против которого и введён конверт.

**`cache_effective_after_seconds` — ОПЦИОНАЛЬНОЕ поле, и CRM его сегодня не показывает.** Оператору задержка сообщается только по факту правки — из `effective_after_seconds` ответа `PATCH` (он авторитетнее: относится к конкретному изменению). Прежняя формулировка «используется как ожидаемая задержка до первой правки» **снята как неверная** — потребителя у поля нет.

⛔ **Обязательным в схеме CRM это поле быть не должно.** Обязательность неиспользуемого поля превращает безобидное умолчание бэка в `schema_mismatch` ⇒ `capabilities: null` ⇒ **страница молча становится read-only при любом праве** — отказ в функции из-за поля, которое никто не читает. **Норма для схем CRM — критерий обязательности поля `capabilities` (ровно один):** поле обязательно **только если у его отсутствия НЕТ определённого безобидного поведения И отсутствие обязано отработать fail-closed**. По этому критерию:

| Поле | В схеме CRM | Почему |
| --- | --- | --- |
| **`features`** | **обязательно** | у отсутствия нет безобидного смысла: без него запись не подтверждена, и единственный безопасный исход — read-only. Fail-closed здесь и есть требуемое поведение |
| **`limits`** | **опционально** | у отсутствия есть **определённое** поведение (§7.2): клиентская проверка границ не выполняется, форма работоспособна, отказ ловит бэк (`400`/`422`, §7.3). Делать поле обязательным значит превращать это штатное состояние в `schema_mismatch` ⇒ `capabilities: null` ⇒ read-only — то есть **сделать описанный путь деградации недостижимым** |
| `contract_version`, `cache_effective_after_seconds` | **опциональны** | потребителя в CRM нет вовсе |

⚠️ Прежняя редакция этой нормы относила к обязательным и `limits` — **ошибка**: она прямо противоречила §7.2 («`limits` отсутствует целиком ⇒ проверки границ нет, форма остаётся работоспособной») и обнуляла его. Если поле когда-нибудь начнут показывать оператору — тогда же появляется строка в словаре ДС, а не раньше.

### §8. Идемпотентность, конфликт и границы

- `PATCH` **идемпотентен** — подтверждающая модалка не вводится (решение владельца), но правка обязана быть **видимой**: ответ несёт `previous_tokens`, CRM показывает **дельту** в тосте (`1000 → 1500`) и пишет её в аудит (§10). Правка токенов — глобальное действие без отката, поэтому дельта обязательна, а не желательна.
- **`previous_tokens` покрывает ТОЛЬКО `tokens`. У `avatar_tokens` авторитетного «прежнего» в контракте НЕТ** — поля `previous_avatar_tokens` не существует, и вводить его в этой волне **не будем** (контракт заморожен и уже реализуется второй командой; renegotiation ради одной строки тоста дороже пользы). Отсюда две **обязательные** нормы:
  - **Подстановка `previous_tokens` в дельту аватар-токенов ЗАПРЕЩЕНА.** Это ложное утверждение о **другой** денежной величине, и цена его выше, чем отсутствие дельты: увидев «Токены продукта: 1000 → 60» после правки аватар-токенов `50 → 60`, оператор пойдёт «исправлять» токены продукта и изменит начисление всем будущим покупкам — ровно тот необратимый исход, ради предотвращения которого дельта и введена.
  - **Дельта аватар-токенов выводится из клиентского снимка** — из значения, которое было показано оператору до правки (новое приходит в ответе). Источник честный («вот что вы изменили»), но **не авторитетный**: между загрузкой и правкой значение мог сменить другой оператор, а `if_updated_at` защищает только при непустом `updated_at`. Долг зафиксирован — [TD-080](../100-known-tech-debt.md); при следующем пересмотре контракта правильное решение — `previous_avatar_tokens` в ответе `PATCH`. Нет клиентского снимка ⇒ тост **без дельты**, а не с подставленной чужой (нормативные строки — [08-design-system.md](../08-design-system.md#локализация-страницы-продукты-и-тарифы-нормативный-словарь)).
- `if_updated_at` — опциональная защита от «двух операторов»: CRM отправляет `updated_at` элемента, который видел оператор; расхождение → `409` → `backend_admin_conflict` → тост «обновите страницу» + refetch.
- `changed: false` — повтор с тем же значением; UI показывает нейтральный тост «Значение не изменилось», а не ошибку.

### §9. `X-Admin-Actor` — заявление, а не аутентификация

CRM шлёт `X-Admin-Actor: crm:<user_uuid>` на каждом `PATCH`. Заголовок **не аутентифицирует** актора: единственная аутентификация — `X-Admin-Key`, общий для всей CRM. Значение пригодно для корреляции в логах бэка и **непригодно** как основание отчёта «кто менял». Формулировка обязана быть записана дословно в докстроке клиента и в module-docs — иначе следующий читатель построит на нём отчётность как на достоверной.

### §10. Аудит правок — существующее событие, новые действия

Правки пишутся **существующим** аудит-механизмом `backend_admin_action` ([ADR-069](ADR-069-backend-users-page-admin-contract.md) §5), без новой таблицы и без нового формата:

- поле «пользователь-цель» становится **опциональным** (у правки каталога субъекта-пользователя нет);
- новые действия: **`product_tokens_updated`**, **`pricing_updated`**;
- в детали пишется **дельта** (`1000->1500`), взятая из `previous_tokens` ответа бэка;
- **деталь обязана называть, КАКОЕ поле изменено.** `previous_tokens` относится только к `tokens`, поэтому при правке **аватар**-токенов запись вида `tokens=1000->1000` и лжива, и слепа: она сообщает о правке, которой не было, и умалчивает о той, которая была. Норма: **`tokens=<prev>-><new>` попадает в `detail`, ТОЛЬКО если `tokens` был в теле запроса**; **`avatar_tokens=<new>`** — если в теле был он (авторитетного прежнего значения нет, см. §8, поэтому пишется только новое). Правка обеих величин одним `PATCH` → **обе** части в одной записи. Аудит — единственный постоянный след глобального необратимого изменения, поэтому «примерно верная» запись здесь хуже отсутствующей;
- событие пишется **только после успеха бэка** — отказ бэка аудит не порождает (иначе лог утверждал бы об изменении, которого не было);
- секреты (`X-Admin-Key`) в аудит и логи не попадают — инвариант [ADR-069](ADR-069-backend-users-page-admin-contract.md)/[05-security.md](../05-security.md#reveal-секретов-по-требованию-adr-035) не ослабляется.

## Альтернативы (отклонены)

| Альтернатива | Почему отклонена |
| --- | --- |
| Хранить каталог продуктов/тарифов в БД CRM (синк) | Два дома у денежной величины; при расхождении неизвестно, по какому значению бэк начислил. Прямо противоречит [ADR-069](ADR-069-backend-users-page-admin-contract.md) §3, который здесь подтверждается |
| Расширить `backend-users` (тот же роутер и то же право `edit`) | Смешивает операцию над одним пользователем с глобальным изменением цены для всех; ресурсы не вложены в пользователя; один роутер с двумя разными гейтами (§2) |
| Только probe, без `/capabilities` | Probe отвечает на вопрос «где префикс», а не «что бэк умеет». Без `features` признак записи пришлось бы выводить из наличия поля `tokens` — запрещено инвариантом 6 |
| Только `/capabilities`, без probe | При холодном кэше 404 на новом пути маппится как «контракт не реализован» и префикс не кэшируется (§4а) — v1-функции страницы «Юзеры бэков» деградируют из-за вызова расширения |
| Сводная маржа за период (отчёт) | Владелец: себестоимость нужна **на уровне отдельного запроса**; агрегат за период потребовал бы либо хранилища в CRM, либо тяжёлого агрегирующего эндпоинта у каждого бэка |
| Модалка подтверждения на правку токенов | `PATCH` идемпотентен, значение — один скаляр в ячейке; трение без выигрыша. Видимость обеспечивается дельтой в тосте и аудитом (§8). Решение владельца; при появлении требования вводится отдельно |
| Отдельный CRM-эндпоинт `GET …/capabilities` | Рассинхрон «список отдельно, карандаши отдельно»: аффорданс правки перестаёт быть частью того же снимка, что и данные. Отклонён **не** ради экономии запросов — конверт их, наоборот, добавляет (4 upstream против 3, §7.2), и это осознанная цена атомарности |
| Новый код ошибки на неизвестный `product_id` | Существующего `backend_admin_bad_request` достаточно: бэк отдаёт `400` с `detail`, CRM транзитом показывает его текст (§6) |

## Последствия

> **Статуса реализации в этом ADR НЕТ — и не должно быть.** ADR фиксирует **предписание** и его основание; факты о состоянии дерева живут в **датированных** домах: [modules/backend-economics §Состояние](../modules/backend-economics/README.md#состояние-замер-на-замороженном-дереве-2026-08-07) и [README §Статусы модулей](../README.md#статусы-модулей). Так устаревает только датированный блок, и это видно по его дате.

- **Новое в CRM (предписание):** роутер `/api/backend-economics` (+ сервис, схемы, резолвер источника), новые методы клиента бэков под расширенные пути, два новых кода ошибок, ключ каталога прав `backend-economics` (`view`/`edit`), пункт навигации и страница «Продукты и тарифы», колонки «Списано токенов» и «Себестоимость» в истории запросов пользователя. Модуль — [modules/backend-economics](../modules/backend-economics/README.md), контракт CRM — [04-api.md#backend-economics](../04-api.md#backend-economics), UI — [08-design-system.md](../08-design-system.md#страница-продукты-и-тарифы-нормативно-adr-072).
- **Собственных таблиц и миграций модуль не добавляет** (§3).
- **Совместимость:** бэк уровня v1 продолжает работать без изменений — страница «Юзеры бэков» не деградирует (probe идёт по v1-пути), страница «Продукты и тарифы» показывает информационное состояние «бэк не поддерживает расширение» (не ошибку и не «пользователь не найден») **в обеих таблицах**: у «Тарифов» — по коду `backend_admin_extension_not_supported`, у «Продуктов» — **выводом из данных** (`200` без `tokens` ни у одного элемента), см. §1.1. Это самый частый случай на старте — расширение пока не реализовано ни одним бэком, поэтому поведение задано нормой, а не оставлено исполнителю.
- **Путь расшифровки admin-ключа** становится общим для двух сервисов (выносится в общий резолвер источника) — security-critical код дублировать во второй сервис нельзя. **Рефакторинг идёт вместе с тестами** — предписание безусловное: вынос пути расшифровки ключа без покрытия обоих сервисов недопустим независимо от того, каково покрытие на момент чтения (сценарии — [06-testing-strategy.md](../06-testing-strategy.md#backend-users--backend-economics-adr-069--adr-072)).
- **Замороженный контракт-тест каталога прав** обязан быть приведён к новому каталогу в том же проходе — иначе CI красный при корректном изменении.
- **Правка тарифа меняет не «отчётную цифру»:** у бэка тот же тариф обслуживает пользовательские пути расчёта стоимости генерации. Это обязано быть названо в описании операции для оператора.
- Заведены [TD-078](../100-known-tech-debt.md) (кэш префикса admin-клиента не инвалидируется при смене домена бэка) и [TD-079](../100-known-tech-debt.md) (примитив инлайн-правки без пропа ошибки и числового режима).
- Реализация расширения **на стороне каждого бэка** — отдельная задача в его репозитории; до неё бэк остаётся на v1.
