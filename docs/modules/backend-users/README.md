# Модуль «Пользователи бэков» (backend-users)

Страница управления пользователями внешних бэков из CRM: объединённый список
(поиск, фильтр по приложению/периоду/платности, сводка «всего/платных/сумма
оплат/CR%»), карточка пользователя (баланс, тариф, экономика, генерации,
истории оплат/запросов) и admin-операции «Начислить токены» / «Установить
план». Решение — [ADR-069](../../adr/ADR-069-backend-users-page-admin-contract.md);
**[ADR-080](../../adr/ADR-080-backend-users-snapshot-and-api-costs.md)** (`implemented`, сверка состава 2026-08-19; прогоны (backend 1854 passed, frontend зелёный, RBAC e2e целевой роли) — по измерениям `qa`/reviewer, architect'ом не перепроверялись) перевёл список
на Postgres-снимок, скрывает бэки без Admin API Key и добавляет блок «Расходы API».
API — [04-api.md#backend-users](../../04-api.md#backend-users).

## Принцип: «список из снимка, карточка live» ([ADR-080](../../adr/ADR-080-backend-users-snapshot-and-api-costs.md))

> **⚠️ Прежний принцип «CRM — прокси БЕЗ собственного хранилища; все данные читаются на лету»
> ОТМЕНЁН** ([ADR-080](../../adr/ADR-080-backend-users-snapshot-and-api-costs.md), отменяет
> [ADR-069](../../adr/ADR-069-backend-users-page-admin-contract.md) §3 **для этого модуля**;
> подтверждение той же нормы в [ADR-072](../../adr/ADR-072-crm-admin-api-v11-economics.md) §3
> **сужено** до [backend-economics](../backend-economics/README.md), где копий по-прежнему нет).
> Модуль **добавляет две таблицы и миграцию** — прежняя запись «БД-миграций нет» недействительна.

Данные страницы приходят из бэков по универсальному **CRM Admin API contract v1**, но
**по двум разным путям**:

| Путь | Источник | Свежесть |
| --- | --- | --- |
| `GET /api/backend-users` (**список + сводка + расходы**) | **Postgres-снимок** `backend_user_snapshot_sources` + `backend_user_snapshots` ([03-data-model.md](../../03-data-model.md#таблицы-снимка-юзеры-бэков-backend_user_snapshot_sources-backend_user_snapshots--adr-080), миграция `0040_backend_users_snapshot`) | до `BACKEND_USERS_SNAPSHOT_INTERVAL_SEC` (900 с); фактический возраст — в поле `snapshot_at` |
| `stats` **при заданном периоде** | **live**, один `GET {P}/stats` на бэк | сейчас |
| карточка, платежи, запросы, продукты, `POST …/tokens`, `POST …/subscription` | **live**, прямой вызов бэка | сейчас |

**Снимок не источник истины:** он read-only-зеркало, его возраст показывается оператору, а
после успешных мутаций выполняется **best-effort touch** строки снимка (§ [Воркер](#фоновый-воркер-backenduserssnapshotservice-нормативно-adr-080)).

Условия участия бэка:

1. Бэк добавлен в реестр «Бэки» и отвечает на health-check.
2. В карточке бэка задан **Admin API Key** (`admin_api_key_encrypted`, Fernet,
   [ADR-040](../../adr/ADR-040-backend-relations-secrets-reverse-lookup.md)).
   Ключ расшифровывается в памяти обработчика и уходит в бэк заголовком
   `X-Admin-Key`; во frontend/логи/**снимок** не попадает.
   > ⛔ **Бэк БЕЗ Admin API Key на странице НЕ отображается** ([ADR-080](../../adr/ADR-080-backend-users-snapshot-and-api-costs.md) §1):
   > он не участвует в снимке и **не попадает в `errors[]`**. Сообщение
   > «Admin API Key не задан в CRM — бэк НЕ опрошен» **упразднено**.
3. Бэк реализует контракт v1 под ОДНИМ из префиксов: `/api/billing/admin` или
   `/v1/admin` (эталонный текст контракта хранится у владельца:
   `BA/crm-admin-api-contract.txt`).

## CRM Admin API contract v1 (сводка)

Все эндпоинты — под `X-Admin-Key` (constant-time сравнение; пустой ключ в env
бэка → fail-closed 401). Даты — ISO 8601 UTC; ошибки — `{ "detail": ... }`;
списки — только с пагинацией `limit` (≤100) / `offset`.

| Эндпоинт (относительно префикса) | Назначение |
| --- | --- |
| `GET /users` | список: `total` + `items[]` (`id`, `external_id`, `is_paid`, `payments_count`, `renewals_count`, `tokens`, `subscription_active`, `subscription_expires_at`, `plan_id`, `registered_at`), сортировка `registered_at DESC` (нормативно — на ней построен merge) |
| `GET /users/{id}` | карточка: `balance`, `subscription`, `revenue\|null`, `media_stats\|null` (опциональные блоки — `null`, а не 404/500) |
| `GET /users/{id}/payments` | история оплат, `occurred_at DESC` |
| `GET /users/{id}/requests` | история запросов, `sent_at DESC`; не хранит — `{total:0, items:[]}`. **v1.1:** элемент += `tokens_spent` (number\|null), `provider_cost_usd` (number\|null), `refunded` (**bool в контракте бэка**) — **все три опциональны для читателя**: бэк уровня v1 их не отдаёт, CRM нормализует отсутствие в `null` ⇒ **в схеме ОТВЕТА CRM `refunded` — `bool \| null`** ([04-api.md](../../04-api.md#backend-users); `null` ≠ `false`), [ADR-072](../../adr/ADR-072-crm-admin-api-v11-economics.md) §1.1 |
| `GET /stats` | `users_total`, `paid_users`, `payments_sum_usd` (CR% считает CRM) |
| `GET /products` | тарифы для «Установить план»: `product_id`, `name`, `price` (str\|null), `period` (str\|null). **v1.1:** элемент += `tokens` (int), `avatar_tokens` (int\|null), `grantable` (bool), `updated_at` (ISO\|null); параметр `scope=grantable\|all` (**по умолчанию `grantable`** — сегодняшнее поведение формы «Установить план» сохраняется; `scope` эта страница **не шлёт**). Все поля v1.1 — **опциональные** ([ADR-072](../../adr/ADR-072-crm-admin-api-v11-economics.md)). **v1.2:** элемент += **`archived`** (bool, опц. — [ADR-073](../../adr/ADR-073-products-archive-and-price-columns.md)); ⚠️ **`scope=grantable` МОЖЕТ вернуть архивные** (сервер по `archived` **не отбирает никогда** — это поле, а не фильтр; оси ортогональны: `scope` — право выдачи, `archived` — товарный вид) |
| `POST /users/{id}/tokens` | `{amount}`; **НЕ идемпотентен**; отрицательное — списание; минус-баланс → 400 |
| `POST /users/{id}/subscription` | `{product_id, expires_in_days, grant_id}`; **идемпотентен** по `grant_id`; продление активной подписки добавляет дни |

> **Расширения v1.1 «экономика»** ([ADR-072](../../adr/ADR-072-crm-admin-api-v11-economics.md)) —
> `PATCH /products/{id}`, `GET`/`PATCH /pricing`, `GET /capabilities` плюс новые поля
> двух эндпоинтов выше — **и v1.2 «архив»** ([ADR-073](../../adr/ADR-073-products-archive-and-price-columns.md)):
> поле `archived` в элементе `GET /products` и в теле его `PATCH`. Дельта и инварианты —
> [modules/backend-economics](../backend-economics/README.md#дельта-контракта-v11-экономика-и-v12-архив-только-новое-относительно-v1);
> здесь не дублируются. Расширения **аддитивны**: бэк уровня v1 работает без изменений,
> эта страница не деградирует (детекция префикса идёт по v1-пути `GET /products`).

### Архивные продукты в форме «Установить план» (нормативно, [ADR-073](../../adr/ADR-073-products-archive-and-price-columns.md) §5)

Правило живёт здесь, потому что **форма принадлежит этой странице**, а её UI-строка
физически лежит в словаре секции «Продукты и тарифы» дизайн-системы (собственной секции
у страницы «Юзеры бэков» в ДС нет). Исполнитель формы обязан найти правило в ТЗ **своего**
модуля, а не в словаре чужой страницы.

- **Форма архивные продукты НЕ фильтрует.** `archived` и `grantable` **ортогональны**:
  архив — товарный вид витрины, `grantable` — право выдачи (env-список бэка). Выдать
  архивный план — **законная операция**, и скрыть опцию значило бы молча лишить оператора
  её. Начисление по архивным продуктам работает как обычно.
- **Но архивная опция ПОМЕЧАЕТСЯ.** Подпись получает суффикс — **нормативная строка одна,
  и она в словаре**: [08-design-system.md § Локализация страницы «Продукты и тарифы»](../../08-design-system.md#локализация-страницы-продукты-и-тарифы-нормативный-словарь),
  строка «Пометка архивной опции в форме «Установить план»». Дословно здесь **не
  дублируется** (одна строка — один дом).
- **Почему обязательно и то и другое:** `scope=grantable` **может вернуть архивные**
  (сервер по `archived` не отбирает никогда). Без пометки оператор не отличит снятую с
  витрины позицию от активной — операция доступна, а её характер скрыт; это «честность
  наполовину», против которой §5 и написан.
- **Бэк без поддержки архива** поля `archived` не отдаёт ⇒ помечать нечего, форма
  работает как прежде.

## Реализация в CRM

- `infra/backend_admin_client.py` — httpx-клиент: автоопределение префикса
  (404 на кандидате → следующий; рабочий кэшируется в памяти по id бэка),
  таймауты `BACKEND_CHECK_TIMEOUT_SEC` на все фазы, маппинг ошибок бэка в
  `AppError` (401/403 → `backend_admin_rejected`; оба префикса 404 →
  `backend_admin_not_supported`; **400 И 422 → `backend_admin_bad_request`**; **409 →
  `backend_admin_conflict`**; сеть/5xx → `backend_admin_unavailable`).
  **Клиент общий с [backend-economics](../backend-economics/README.md)**
  ([ADR-072](../../adr/ADR-072-crm-admin-api-v11-economics.md) §4): детекция префикса
  идёт **всегда по v1-пути `GET /products`** (расширенные пути её не выполняют), а
  семантика 404 задаётся вызывающим **явно, без значения по умолчанию** —
  `CONTRACT` → `backend_admin_not_supported`, `USER` → `backend_user_not_found`
  (**только пути `/users/*`**), `EXTENSION` → `backend_admin_extension_not_supported`.

> **Маппинг `422` действует и на путях v1 — это изменение поведения ЭТОЙ страницы**
> ([ADR-072](../../adr/ADR-072-crm-admin-api-v11-economics.md) §7.3; норма написана про
> «бэк» без ограничения путями, а клиент — общий). Раньше `422` от бэка уходил в ветку
> «прочий не-2xx» и давал **`502` с голым «Ошибка бэка (HTTP 422)»**; теперь это
> **`400 backend_admin_bad_request`** с текстом причины. Практически заметно на
> `POST /users/{id}/tokens` и `POST /users/{id}/subscription`: отказ валидации тела у
> бэка (например, слишком большая сумма) виден оператору как «поправьте введённое
> значение», а не как «бэк сломан». **Текст причины:** `detail`-строка — транзитом;
> `detail`-**список** (формат `422` FastAPI) — `msg` первого элемента (+ поле из `loc`);
> не удалось извлечь — фолбэк **«Бэк отверг значение: не прошло проверку на стороне
> бэка»**. Соседние статусы **не** поглощены: `405`/`429`/`5xx`/`3xx` по-прежнему
> `backend_admin_unavailable`, `409` и `401`/`403` — свои коды.

> **Следствия probe для ЭТОЙ страницы** ([ADR-072](../../adr/ADR-072-crm-admin-api-v11-economics.md) §4а.1).
> Probe идёт при **любом** холодном вызове, включая пути `/users*`, поэтому:
> **(1)** первый вызов процесса к бэку делает **один дополнительный upstream-запрос**
> (`GET {P}/products` перед запрошенным путём) — цена, уже принятая
> [ADR-069](../../adr/ADR-069-backend-users-page-admin-contract.md) §2;
> **(2)** бэк с **неработающим `/products` при рабочем `/users`** теперь **блокирует
> страницу** (`502 backend_admin_not_supported`), тогда как прежде она бы работала —
> принято осознанно: `/products` обязателен в v1 и является нормативным probe-путём,
> так что такой бэк нарушает контракт, и скрывать это не следует;
> **(3) побочно закрыт латентный дефект:** прежде при холодном кэше `404` от
> `GET /users/{id}` **несуществующего** пользователя давал `backend_admin_not_supported`
> вместо `backend_user_not_found` (в ветке детекции семантика 404 не учитывалась —
> ветка детекции префикса в `_request`). Теперь префикс определяется
> probe'ом заранее, и `404` попадает в ветку известного префикса.
- `services/backend_user_service.py` — режим «Все приложения»: конкурентный
  fan-out (семафор 5) по бэкам с admin-ключом, merge по `registered_at DESC`,
  суммирование stats; упавший источник → `errors[]` ответа (partial data), при
  единственном источнике ошибка пробрасывается. Ответы бэка валидируются
  Pydantic-схемами (`schemas/backend_user.py`): не по контракту → 502.
  > **⛔ ОТМЕНЕНО [ADR-080](../../adr/ADR-080-backend-users-snapshot-and-api-costs.md) §1: «бэк реестра БЕЗ admin-ключа
  > тоже попадает в `errors[]`».** Такие бэки **скрываются**; `errors[]` означает
  > **только** «источник опрашивался и не ответил». Константа `_ADMIN_KEY_NOT_SET`
  > и генерация ошибок из `unqueried` удаляются, `_resolve_sources` переходит на
  > `list_with_admin_key()`.
  >
  > **Прод-инцидент `selquro` при этом остаётся закрытым — другим средством.**
  > Исходная беда была в том, что «Ничего не найдено» неотличимо от «бэк не
  > опрашивался». Теперь это различает **состав фильтра приложений**: он строится по
  > `has_admin_api_key`, то есть оператор видит, какие приложения вообще участвуют в
  > поиске; пустое состояние прямо говорит «подключите бэк с Admin API Key».
  > Постоянная жёлтая плашка при **штатной** конфигурации обесценивала
  > предупреждение о настоящем сбое — ради этого норма и пересмотрена.
  >
  > **Регресс-гейт инвертируется:** `tests/integration/test_backend_users_unqueried_sources.py`
  > → `test_backend_users_keyless_hidden.py` (`errors == []` при наличии бэка без ключа).
  > Файл-гейт **обязан остаться** — иначе возврат старой ветки пройдёт молча.
  > `BackendAdminSourceResolver.list_split()` сохраняется, только если у него остаётся
  > потребитель; иначе упрощается до `list_with_admin_key()` — это решение исполнителя,
  > а не норма.

## Фоновый воркер `BackendUsersSnapshotService` (нормативно, [ADR-080](../../adr/ADR-080-backend-users-snapshot-and-api-costs.md))

Новые файлы: `app/models/backend_user_snapshot.py`, `app/repositories/backend_user_snapshot_repository.py`, `app/services/backend_users_snapshot_service.py`. Регистрация — `asyncio.create_task(...)` в `lifespan` (`backend/app/main.py`), рядом с существующими мониторами.

**Канон — `BackendMonitorService`** (`backend/app/services/backend_monitor_service.py:266-278`, сверка 2026-08-19): немедленный `refresh_once()` при старте, затем `while True: refresh_once(); await asyncio.sleep(interval)`; **исключение итерации логируется и задачу не валит**. Брокер/внешний кэш **не вводятся** ([ADR-006](../../adr/ADR-006-async-provisioning-bez-brokera.md)/NFR-1) — это девятый воркер того же класса, а не новый инфраструктурный компонент.

> **`sleep` ПОСЛЕ завершения итерации, а не фиксированный тик.** Обход крупного бэка может занять больше интервала; при тиковой схеме циклы бы накладывались и удваивали нагрузку на источник. Цена — фактический период ≥ `BACKEND_USERS_SNAPSHOT_INTERVAL_SEC`; она честно показывается оператору полем `snapshot_at`.

**Fan-out** по бэкам с admin-ключом, **`Semaphore(BACKEND_USERS_SNAPSHOT_CONCURRENCY)` — по умолчанию 2** (снижено с 5 хотфиксом 2026-08-20 — см. [§Бережность к источнику](#бережность-к-источнику-нормативно-амендмент-adr-080-2026-08-20)). Алгоритм на один бэк:

1. Загрузить **fingerprints** снимка одним `SELECT`: `user_id → (tokens, payments_count, renewals_count, is_paid, subscription_active, subscription_expires_at, plan_id)`.
2. **Полный** постраничный обход `GET {P}/users?limit=100` — **без** ограничения `_MAX_WINDOW` (оно защищало интерактивный запрос; здесь запрос фоновый). Батч-upsert `ON CONFLICT (backend_id, user_id) DO UPDATE`, **пишутся только новые и изменившиеся строки** (changed-only-writes против churn и autovacuum). Множество изменившихся = **dirty-set**.
3. `DELETE` строк снимка, отсутствующих в источнике — **ТОЛЬКО при полностью успешном обходе**. Оборванный обход снимок не прореживает.
4. `GET {P}/stats` → `stats_users_total` / `stats_paid_users` / `stats_payments_sum_usd` строки источника.
5. Экономика: `GET {P}/users/{id}` по **dirty-set** + backfill-квота `BACKEND_USERS_SNAPSHOT_REVENUE_BATCH` (2000) на строки с `revenue_refreshed_at IS NULL`, порядок добора — `registered_at DESC`. Всё добрано ⇒ `revenue_backfill_done = true`.
   - ⚠️ **Метка `revenue_refreshed_at` ставится и при карточке БЕЗ блока `revenue`** (`api_cost_usd` остаётся `NULL`) — перечитывать такую строку бессмысленно, она обязана покинуть очередь. Поэтому у бэка **уровня v1** `revenue_backfill_done` честно становится `true` при **навсегда заниженной** сумме.
   - По **первой успешно добранной карточке цикла** выставляется **`revenue_supported`** строки источника: блок `revenue` есть → `true`, нет (`null` по контракту §4.5) → `false`. Признак **пересматривается каждый цикл** — бэк, внедривший v1.1, переключается в `true` без ручного вмешательства.
6. Пересчёт `api_costs` источника: `SUM` по `jsonb_each_text(api_cost_providers)` с нормализацией ключей; `refreshed_at = now()`, `error_message = NULL`, `failed_at = NULL`.
7. **Любое исключение** → прошлый снимок **не трогается**, пишутся `error_message` / `failed_at`. Устаревшие данные с честной меткой возраста лучше пустого экрана.
   - ⚠️ **[Q-BU-2](../../99-open-questions.md) (сужен 2026-08-20):** backoff и `break` **реализованы**; открыт только признак «обход не завершён» — без него бэк, чей обход систематически не доходит до конца, даёт вечное «Снимок формируется…» при уже накопленных строках.

**Нормализация провайдера `_normalize_provider` (нормативно):** `openai`/`gpt*` → `openai`; `anthropic`/`claude*` → `anthropic`; `fal`/`fal.ai` → `fal`; **всё остальное → `other`** (незнакомый провайдер **не теряется**). Регистронезависимо, по префиксу. Нормализация выполняется **при агрегации**, а не при записи: в `backend_user_snapshots.api_cost_providers` лежат **сырые** ключи бэка, чтобы смена правила не требовала повторного обхода.

**Best-effort touch после мутаций.** Успешный `POST …/tokens` / `POST …/subscription` обновляет строку снимка значениями **из ответа бэка** (`tokens`, `subscription_active`, `subscription_expires_at`). ⚠️ **Только непустые поля:** `tokens` — **`float | null`**, и `null` означает «бэк поле не прислал» ([ADR-072](../../adr/ADR-072-crm-admin-api-v11-economics.md) §1.1), а **не** «баланс обнулился» — записать его в снимок значило бы показать оператору ложный ноль. Незаполненные поля ответа сохраняют прежнее значение строки до следующего цикла воркера. **Провал touch логируется и НЕ превращает успешную admin-операцию в ошибку** — у бэка она уже состоялась (тот же принцип «сначала факт, затем интерпретация», что в [ADR-073](../../adr/ADR-073-products-archive-and-price-columns.md) §8; долг класса — [TD-081](../../100-known-tech-debt.md)).

**Тестируемость.** В интеграционных тестах `lifespan` не выполняется, поэтому воркер тестируется **прямым вызовом `refresh_once()`** — тот же приём, что у `BackendMonitorService`. Транспорт — `FakeAdminTransport` (`backend/tests/backend_admin_helpers.py`).

### Бережность к источнику (нормативно, амендмент [ADR-080](../../adr/ADR-080-backend-users-snapshot-and-api-costs.md) 2026-08-20)

**Прод-инцидент 2026-08-20:** воркер **выбивал источники** — бэки отвечали `429`/`500` под его же нагрузкой. Причина структурная: воркер единственный ходит в бэк тысячами запросов подряд и сам доводит его до rate-limit. Хотфикс (сверка `backend/app/services/backend_users_snapshot_service.py` 2026-08-20) — четыре меры:

| Мера | Как | Параметр (дефолт) |
| --- | --- | --- |
| **Backoff на `429`/`5xx`** | `_with_retry` вокруг **всех** upstream-вызовов цикла: числовой **`Retry-After`** источника, если есть (`min(retry_after, cap)`), иначе `base * 2^attempt` с потолком и **джиттером** (50–100 % окна) | `RETRY_ATTEMPTS=5`, `RETRY_BASE_SEC=1.0`, `RETRY_CAP_SEC=30.0` |
| **Троттлинг** | пауза между страницами обхода и карточками добора; `0` выключает | `PAGE_DELAY_SEC=0.3` |
| **Конкурентность fan-out** | `Semaphore(...)`, снижена с 5 | `CONCURRENCY=2` |
| **`break` при бесполезной странице** | страница без единого **нового** `user_id` ⇒ пагинация источника сбита, дальше те же строки. ⛔ **Обход считается НЕПОЛНЫМ ⇒ цикл — ОТКАЗ:** `delete_rows` пропускается, пишется `_record_failure` («Источник повторяет страницу — обход прерван»), снимок прошлого цикла цел. Событие `backend_users_snapshot_walk_stalled` | — (`Q-BU-2` вариант «а») |

**Что НЕ ретраится:** `401`, `404`, `400`, `422` и транспортные ошибки — повтор там бессмысленен, отказ окончателен.

⚠️ **Ретраи существуют ТОЛЬКО в воркере.** Интерактивные пути (`/users/{id}`, `/payments`, `/requests`, обе мутации) повторов **не получают**: там ждёт человек, и лишние 30 секунд хуже честной ошибки.

⚠️ **Исчерпание попыток контракта отказа НЕ меняет:** наружу уходит та же ошибка ⇒ цикл этого бэка падает, пишутся `error_message`/`failed_at`, **снимок прошлого цикла цел** (инвариант 4 выше в силе).

⚠️ **Паузы берутся только при ЗАКРЫТОЙ сессии БД.** Обход и добор карточек идут вообще без открытой сессии; пауза с открытой держала бы транзакцию `idle in transaction` на все секунды backoff'а и выбирала бы пул — против канона коротких сессий и прямо в сторону [TD-088](../../100-known-tech-debt.md).

⛔ **Штатное завершение обхода — ТОЛЬКО `len(items) < limit`** (и пустая первая страница). `break` по бесполезной странице и упор в **`_MAX_PAGES = 50 000`** штатными **не являются**: оба помечают обход неполным (`complete = False`) и уводят цикл в отказ **до** шага `DELETE`. Так инвариант 3 §Инвариантов записи («`DELETE` только при полном успешном обходе») защищён машинно — флагом, а не дисциплиной вызывающего.

> **Почему это critical, а не педантизм** (воспроизведено `backend-reviewer` 2026-08-20). Источник, повторяющий окно, отдаёт заведомо неполный набор `user_id`. Если считать такой цикл успешным, разность «было в снимке − встречено в обходе» объявит пропавшими **всех, до кого обход не добрался**, и `DELETE` их вычистит — а `refreshed_at` проставится, то есть UI покажет свежий снимок **без** этих пользователей и без признака беды. Потеря тихая и накапливающаяся; отказ цикла честнее.

**Контракт наружу не изменился.** Новый подкласс `BackendAdminUpstreamStatus` (`upstream_status`, `retry_after_sec`, `backend/app/errors.py`) сохраняет статус источника **машинно** — чтобы решение «ретраить или нет» принималось по числу, а не по разбору текста ошибки; наружу по-прежнему уходит `502` с прежними кодами.

## Блок «Расходы API» (нормативно, [ADR-080](../../adr/ADR-080-backend-users-snapshot-and-api-costs.md))

> **Почему норма живёт здесь, а не в дизайн-системе.** У страницы «Юзеры бэков» **собственной секции в ДС нет** (та же причина, что у [«Архивных продуктов в форме „Установить план“»](#архивные-продукты-в-форме-установить-план-нормативно-adr-073-5) — правило принадлежит странице, а не чужому словарю). Примитивы при этом — **только существующие**: новых компонентов ДС не вводится.

- **Расположение:** второй grid `SummaryCell` **под** существующей сводкой «всего / платных / сумма оплат / CR%» (`frontend/src/pages/BackendUsersPage.tsx:184-198`; сам примитив — `:323`, сверка 2026-08-19).
- **Ячейки:** **«Расход OpenAI»** / **«Расход Anthropic»** / **«Расход Fal»**; **«Прочее»** — **только при `other_usd > 0`** (постоянная ячейка `$0.00` создавала бы впечатление, что «прочих» провайдеров ждут). Формат — USD **с центами**.
- **Метка свежести (обязательна):** **«Данные на HH:MM»** из `snapshot_at`; `snapshot_at === null` → **«Снимок формируется…»**. Без метки оператор не отличит 15-минутную задержку от сбоя.
- **`partial === true`** → пометка **«расходы ещё собираются»**. Вычисление (нормативно, [ADR-080](../../adr/ADR-080-backend-users-snapshot-and-api-costs.md) §5):

  ```
  partial = ∃ участвующий источник:  revenue_backfill_done = false
                                     OR revenue_supported IS FALSE
           OR ∃ запрошенный бэк БЕЗ строки в backend_user_snapshot_sources
  ```

  Флаг покрывает **три** случая: незавершённый backfill карточек, **постоянное** занижение от бэков уровня v1 без блока `revenue` и **запрошенный бэк, у которого ещё нет строки состояния** (добавлен в реестр между циклами воркера). **Третий дизъюнкт — «запрошенный бэк ещё не имеет строки состояния»** (сверка `backend/app/services/backend_user_service.py` 2026-08-19: `len(participating) < len(backend_ids)`). Строка `backend_user_snapshot_sources` заводится воркером, поэтому бэк, добавленный в реестр между циклами, в сумму не входит — и это ровно «сумма неполная». Без третьего дизъюнкта свежедобавленный бэк молча занижал бы итог **без пометки**. **Вырожденный случай:** строк нет **ни у одного** запрошенного бэка ⇒ **`api_costs = null`**, а не `0` с `partial=true` — нулей, которых никто не измерял, показывать нельзя. **Фактическое поведение UI при `api_costs === null` (сверка `frontend/src/pages/BackendUsersPage.tsx` 2026-08-19): блок «Расходы API» РЕНДЕРИТСЯ, но все значения — `—`** (`value={apiCosts ? formatUsdCents(...) : '—'}`); ячейка «Прочее» скрыта (`other_usd > 0` не выполняется), бейдж `partial` не показывается (`apiCosts?.partial`), а причину объясняет подпись свежести «Снимок формируется…» при `snapshot_at === null`. Прочерк честнее скрытия: блок на месте, и видно, что величина не измерена, а не равна нулю. ⚠️ **Считать его только по `revenue_backfill_done` — ДЕФЕКТ:** очередь backfill выбирается по `revenue_refreshed_at IS NULL`, карточка v1-бэка эту метку получает и очередь покидает ⇒ backfill у него «завершён», а сумма занижена навсегда, и пометка исчезла бы именно в неисправимом случае. Различить два состояния **в самом флаге** нельзя (он скалярный) — последствие для оператора одно («сумма неполная»); поимённое разведение — [TD-085](../../100-known-tech-debt.md).
- ⚠️ **Подпись обязана называть период:** показатель **накопительный за всё время (lifetime)**, фильтр периода страницы на него **не действует**. Без этой подписи оператор прочтёт lifetime-сумму как «за выбранный период» — самая дорогая ошибка блока.
- Хуки данных не меняются: оба поля приходят тем же `GET /api/backend-users`; отдельного запроса нет.

## Ограничения

- ~~Merge-пагинация «Все приложения» ограничена окном 1000 строк~~ — **упразднено**
  ([ADR-080](../../adr/ADR-080-backend-users-snapshot-and-api-costs.md) §3): список читается из снимка одним SQL с
  `ORDER BY registered_at DESC, backend_id, user_id`, глубина пагинации не ограничена.
  Окно 1000 было ценой merge по нескольким live-источникам.
- ~~БД-миграций нет — модуль не добавляет таблиц~~ — **недействительно**: модуль добавляет
  **две таблицы** и миграцию `0040_backend_users_snapshot`.
- **Смешанная свежесть**: список (до 15 мин) ↔ карточка (сейчас). Самый заметный случай
  (начисление токенов) закрыт best-effort touch'ем; прочие расхождения живут до одного
  цикла воркера. Возраст данных списка виден в UI (`snapshot_at`).
- **Полный обход крупного бэка может превысить интервал.** Наложение циклов исключено
  паттерном «`sleep` **после** завершения итерации»; 429/паузы источника обрабатываются
  как исключение итерации — снимок при этом сохраняется.
- **Блок «Расходы API» — LIFETIME и может быть занижен**: фильтр периода на него не
  действует, а бэки уровня v1 без блока `revenue` в сумму не входят ([TD-085](../../100-known-tech-debt.md)).
- **Поиск ограничен полями снимка** — `user_id` и `external_id` (паритет с прежним поиском
  у бэка). Расширять его нечем: других полей в контракте `GET {P}/users` нет.
- **Каждый бэк реализует контракт отдельной задачей в СВОЁМ репозитории** — v1, а затем
  расширение v1.1 ([ADR-072](../../adr/ADR-072-crm-admin-api-v11-economics.md)). Норма
  CRM от этого не зависит: страница обязана работать и с бэком уровня v1 (поля v1.1
  опциональны), и с бэком без контракта вовсе (`502 backend_admin_not_supported`).
  **Кто из бэков что реализовал — факт о ЧУЖОМ дереве и здесь не фиксируется**:
  датированный срез — в [§Состояние](#состояние-замер-на-замороженном-дереве-2026-08-07),
  актуальное состояние — в репозитории соответствующего бэка.
